## Findings

### 1. [Medium] `build_refs.sh` never creates `$BINS`, and the failure surfaces one full build too late

`$BINS/MANIFEST.tsv` is written (header block) and appended to, and `cp "$bin" "$snap"`
writes into `$BINS` — but nothing runs `mkdir -p "$BINS"`. The script uses `set -u`
without `set -e`, so on a fresh checkout the header-redirect failure prints to stderr
and execution continues; the hard stop only comes ~40 minutes later when `cp` fails
after the baseline build completes. The recorded run only succeeded because `bins/`
already existed in this working tree (created out-of-band; repo-root `tmp/` is
gitignored, so a fresh checkout will not have it). Since the commit's stated purpose
is reproducibility, this is the one defect that directly undermines it.

Suggested rewrite — one line before the manifest-header block:

```bash
mkdir -p "$BINS"
if [ ! -f "$BINS/MANIFEST.tsv" ]
```

### 2. [Medium] A failed `worktree_setup.sh` leaves a poisoned worktree that `build_refs.sh` then accepts

If setup dies after `git worktree add` but before submodule materialization (the
window is most of the script), the worktree exists with a parent checkout and no
submodule trees. On re-run, `build_one`'s guard `[ ! -d "$worktree" ]` skips setup,
the HEAD-pin check passes (HEAD resolves fine), and the failure re-surfaces as a
confusing cmake/ninja error. Meanwhile a direct re-run of `worktree_setup.sh` refuses
with "already exists", so there is no clean resume path at all. This is the
"edge case that actually arrives" class the humanize bar asks fresh code to cover.

Suggested rewrite (either one suffices):

- In `worktree_setup.sh`, clean up on failure so the existence checks stay truthful:

  ```bash
  trap 'git -C "$MAIN_REPO" worktree remove --force "$WORKTREE_PATH" 2>/dev/null' ERR
  ```

  (with `set -E`), or explicit removal on each `exit` path.

- Or in `build_one`, probe readiness instead of existence:

  ```bash
  if [ ! -f "$worktree/contrib/llvm-project/llvm/CMakeLists.txt" ]
  ```

### 3. [Low] Fresh reword garbled the recovery instruction in `worktree_setup.sh`

The skill's three-line closing error separates the fix command (the fetch) from what
to re-run (step 6). The condensed fresh version —
`"Fetch it in the main repo, then re-run: git -C %s submodule update --init"` —
now reads as "re-run the submodule update", which repairs nothing in the worktree.
The actual recovery is: fetch in the main repo, remove the partial worktree, re-run
this script.

Suggested rewrite:

```bash
printf "Fix: git -C %s submodule update --init (fetches the missing commit),\n" "$MAIN_REPO" >&2
printf "then remove %s and re-run this script.\n" "$WORKTREE_PATH" >&2
```

### 4. [Low] MANIFEST.tsv is append-only with no rule for which row is current

The commit message calls the manifest "the identity of record", but re-running a
build appends a second row under the same binary name (the `.bin` snapshot is
overwritten by `cp`; the old row's sha then describes nothing on disk). Nothing
states that the last row per name wins.

Suggested rewrite — one clause in the script header (or dedupe before append):

```
#   ...MANIFEST.tsv (append-only; the last row for a given name describes the
#   snapshot currently on disk).
```
