### 2. `prepareDispatchKeyColumns` re-implements the `JoinOnKeyColumns` prep chain
- Location: `src/Interpreters/ConcurrentHashJoin.cpp` lines 620-646 (`DispatchKeyColumns` +
  `prepareDispatchKeyColumns`) vs `src/Interpreters/HashJoin/AddedColumns.cpp` lines 7-22
  (`JoinOnKeyColumns` ctor).
- What: the build-side helper hand-copies the first three steps of the `JoinOnKeyColumns`
  constructor — `JoinCommon::materializeColumns[KeepLowCardinality]` -> `JoinCommon::getRawPointers`
  -> `extractNestedColumnsAndNullMap` — with the same `keep_lowcardinality` predicate
  (`HashJoin::isLowCardinalityType`). The 6-line comment above `DispatchKeyColumns` exists solely to
  assert, in prose, that the two chains match ("the same unwrap chain `JoinOnKeyColumns` applies on
  the probe side") — an invariant currently maintained by parallel editing of two code paths.
- Suggested change: build the same object on both sides. In `dispatchBlock`, replace the helper with
  a `JoinOnKeyColumns` constructed symmetrically to `joinBlock`:
  `JoinOnKeyColumns keys{ScatteredBlock{from_block}, key_columns_names, /*cond*/ {}, join0.getKeySizes().at(0), HashJoin::isLowCardinalityType(...)}`
  (full key list, like the probe), then route by the existing shared slice:
  `computeDispatchSlotIds(join0, routeKeyColumns(keys, join0), rows, num_shards, slot_ids.data())`.
  Deletes the `DispatchKeyColumns` struct, the helper, and the prose-equivalence comment (~27 lines)
  and makes probe/build prep agreement true by construction; `NullableUtils.h` then drops out of
  this TU (finding 1).
- Why non-behavioral: the constructor performs the identical call sequence on the identical inputs,
  so the route columns — and therefore the slot ids — are bit-identical. Added cost is O(columns),
  not O(rows): a COW `Block` copy, a range `Selector` (a `std::pair`), and
  `getColumnAsMask(block, "")` which returns `JoinMask(true, rows)` without touching row data
  (`src/Interpreters/JoinUtils.cpp` line 581).
- Trap to call out for whoever applies it: do NOT pre-slice the names AND still call
  `routeKeyColumns` — `routeKeyColumnCount` drops the trailing key for ASOF unconditionally, so an
  already-sliced ASOF list would lose a second column. Either full names + `routeKeyColumns`
  (recommended, mirrors the probe) or sliced names + `keys.key_columns` directly — not both.
  (Full-names does materialize the ASOF inequality column on the build path too; that column is
  needed by the per-slot insert anyway and the work is per-column, not per-row.)
