# HUMANIZE review — 561c1d21b99 + aa98041d472 (routed probe plan + fused descriptor find)

Report-only. Scope: `src/` changes of both commits, reviewed together (tmp/ evidence ignored).
Line numbers refer to the files as of aa98041d472 (current HEAD). All suggestions are
non-behavioral (comments, naming, wording, commit-message text).

Overall: mechanically clean — Allman throughout (including the new `handle` lambda and
`flatFindKey`), `f`-not-`f()` respected everywhere, backticks correct in nearly all comments,
and the moved `SlotMapDesc` doc was transplanted faithfully. The tells are comment-side and
message-side: the two-collection-points story told at four sites, one mechanism ("the fused
descriptor find") narrated four times with an identical lead sentence, a five-line C++
dependence-rules lecture aimed at the reviewer, two new caps-for-emphasis words, a
"flat"-in-code vs "fused"-in-prose vocabulary split, and commit messages that carry the
branch's internal gate shorthand and skip the backtick house rule.

## Findings

### 1. The two-collection-points story is told at four sites (should fix)
- **Locations:**
  - `src/Interpreters/ConcurrentHashJoin.cpp:234-235` (ctor call): "The freshly built (empty)
    maps already have valid buffers, so plan-time header probes see sized plan arrays;
    `onBuildPhaseFinish` re-collects over the final maps."
  - `src/Interpreters/ConcurrentHashJoin.cpp:909-911` (`onBuildPhaseFinish` call): "The maps
    are final from here on ... so this is the one collection point whose addresses and sizes
    the probes may trust."
  - `src/Interpreters/ConcurrentHashJoin.h:155-159` (member doc): "collected at the end of the
    constructor (plan-time header probes run before any build) and re-collected by
    `onBuildPhaseFinish` when the maps are final."
  - `src/Interpreters/HashJoin/JoinProbeScratch.h:26-28` (`RoutedProbePlan` doc): "collected by
    `ConcurrentHashJoin` when the maps are final (and once at construction, so plan-time header
    probes see sized arrays)."
- **What:** One fact — collect twice: once for plan-time header probes over empty maps, once
  after shrink-to-fit finalizes addresses — restated in full wherever the plan is touched.
  Verbatim restatement at every touching site is the classic generated tell this branch's
  earlier hygiene passes already flagged (the pool-fallback contract, same pattern).
- **Suggested rewording:** Keep the full schedule once, on the member doc in
  `ConcurrentHashJoin.h` (it already reads as the contract). Trim the ctor call site to the
  genuinely local bit: "Empty maps already have valid buffers — plan-time header probes need
  sized arrays." Trim the `onBuildPhaseFinish` site to: "Per-slot `onBuildPhaseFinish` includes
  shrink-to-fit, which moves buffers, so re-collect the final addresses." Drop the
  parenthetical from the `RoutedProbePlan` doc — the struct's header should not narrate its
  collector's schedule ("collected by `ConcurrentHashJoin` when the maps are final" is enough).

### 2. "The fused descriptor find" narrated four times, twice with the same lead sentence (should fix)
- **Locations:** `src/Interpreters/HashJoin/HashJoinRoutedMethodsImpl.h`
  - :192-195 (trait `flat_lookup_supported`): "The fused descriptor-based find of the routed
    plain loop (no ring): ..."
  - :200-204 (`flatFindKey` doc): "The fused descriptor-based find of the routed plain loop:
    ..." — the identical opening clause.
  - :406-407 (loop arm): "The fused descriptor find: two cheap loads (slot id, descriptor) on
    the address path instead of the map-header chase."
  - :630-632 (dispatch): "The cheap-key cursor-capable families run the fused descriptor find
    instead of the map-resolved `findKey`; ..."
- **What:** Two problems. (a) The trait comment describes the *function*, not the predicate —
  a comment on `constexpr bool flat_lookup_supported` should say what makes a family
  supported, not re-explain the find. (b) The loop-arm comment is perf narration ("two cheap
  loads ... instead of the map-header chase") that repeats the commit message; it justifies
  the change to a reviewer rather than telling the next reader something the code doesn't.
  The dispatch comment (:630-632) is the one genuinely load-bearing site — it is the reader's
  map of which key families take which loop.
- **Suggested rewording:** Trait: "The families served by `flatFindKey` when the ring is not
  engaged: cheap-key getters over cursor-capable maps. Unlike the ring it serves every mapped
  shape (ASOF included) and wrapped-chain builds." Function doc: keep as the single full
  description (drop "(no ring)" duplication). Loop arm: delete the sentence entirely — the
  zero-key comment just below (:412-413) is the only non-obvious thing in that arm. Dispatch:
  keep.

### 3. Nested-`if constexpr` lecture talks to the reviewer (should fix)
- **Location:** `src/Interpreters/HashJoin/HashJoinRoutedMethodsImpl.h:397-401`: "The nested
  `if constexpr` matters: `flat_find` is the lambda's own parameter, but the arm's expressions
  only depend on the ENCLOSING template's types, so the trait check (dependent at the
  enclosing definition) is what keeps the arm out of the non-cursor families' instantiations."
- **What:** A five-line lesson-learned about C++ dependence rules — the kind of explanation
  that belongs in the PR description. The one fact worth protecting (do not fold the two
  conditions into one `&&`) fits in a line; the mechanism lecture and the caps "ENCLOSING"
  are tells. The next reader needs the *instruction*, not the standardese derivation.
- **Suggested rewording:** "/// Nested on purpose: the inner trait check keeps the flat arm
  from being instantiated for the non-cursor map families — do not merge it into the
  `flat_find` condition."

### 4. New caps-for-emphasis (should fix)
- **Locations:** `src/Interpreters/HashJoin/HashJoinRoutedMethodsImpl.h:202` "The walk is
  wrap-AWARE (through the tail pad, wrapping at its end)"; :399 "the ENCLOSING template's
  types" (covered by finding 3).
- **What:** Caps-for-emphasis is a generated-text mannerism these reviews have flagged on
  every prior commit of this branch; the moved `SlotMapDesc` comment ("NOT `bufSize - 1`") is

### 5. Vocabulary split: "flat" in code, "fused" in prose; `flat_descs` vs `desc_by_slot` (should fix)
- **Locations:** `src/Interpreters/HashJoin/HashJoinRoutedMethodsImpl.h:197` (`flat_lookup_supported`),
  :206 (`flatFindKey`), :280 (`flat_descs`), :335 (`flat_find`), :633 (`flat`) vs the comments
  and both commit messages, which call the same thing "the fused descriptor find".
- **What:** Two names for one mechanism; a maintainer picks one. Separately, :280 aliases
  `plan.desc_by_slot.data()` as `flat_descs` while the AMAC call four screens down passes
  `plan.desc_by_slot.data()` directly (:593) — the same array reaches its two consumers under
  two spellings, and the new local sits inside the "snapshots of the plan's arrays" block
  whose neighbors are named `maps_data` / `flags_data`.
- **Suggested rewording:** Use "flat find" in prose too (it is the code's name), or rename the
  code to `descFindKey` / `desc_find` if "descriptor find" is preferred — either way, one
  term. Rename `flat_descs` to `descs_data` to match the snapshot-naming of its neighbors and
  pass it to `amacFindPass` as well.

### 6. Slot-0 hash/zero-key stand-in loses `map0`'s justification (nice to have)
- **Locations:** `src/Interpreters/HashJoin/HashJoinRoutedMethodsImpl.h:322` and :410, :419:
  `maps_data[0]->hash(key)` / `maps_data[0]->isZeroKey(key)` against `flat_descs[slot]`.
- **What:** The AMAC pass established this exact pattern with a named member and a one-line
  contract (`AmacProbe.cpp:100-102`: "Hash provider and zero-key checker; reads nothing
  through the object ... so any slot's map serves"). The new sites spell `maps_data[0]` inline
  next to per-`slot` descriptors with no such note; a reader trips on hashing through slot 0
  while probing slot `slot`, and `flatFindKey`'s doc ("the map object only for its
  hash/equality functors") does not say why slot 0's is safe.
- **Suggested rewording:** Hoist a named local next to the other snapshots — `const Map & map0
  = *maps_data[0]; /// hash/zero-key only; stateless, so any slot's map serves (see `map0` in
  `AmacProbe.cpp`)` — and use it in both the prefetcher and the flat arm.

### 7. Block comments embedded in the `M` macros; inconsistent `#define` style in one file (nice to have)
- **Locations:** `src/Interpreters/ConcurrentHashJoin.cpp:273-274` ("/* The descriptor and the
  wrap bit exist only for the cursor-capable ... */ \\") and
  `src/Interpreters/HashJoin/HashJoinRoutedMethodsImpl.h:118-119` ("/* The once-per-build plan
  holds the type-erased map pointers ... */ \\").
- **What:** Backslash-continued `/* */` comments inside macro bodies. It works, but no other
  `APPLY_FOR_JOIN_VARIANTS` macro body in the tree carries comments — the established pattern
  puts them above the `#define` or above the `switch` (compare the comment above the switch at
  `HashJoinRoutedMethodsImpl.h:109-111`). Also, `ConcurrentHashJoin.cpp` now holds two `M`
  macros in different styles: line 141 indented with aligned backslashes, line 268 at column 0
  with ragged ones.
- **Suggested rewording:** Hoist each comment to a `///` line above its `#define M`. Optionally
  match the new macro's indentation to the file's existing one.

### 11. `RoutedProbePlan` lives in the scratch header (nice to have)

- **What:** The branch's own vocabulary distinguishes the once-per-build immutable *plan* from
