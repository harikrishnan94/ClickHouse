Report-only. Scope: `src/` changes only (tmp/ evidence ignored). Line numbers refer to the
files as of f8d4826722d. All suggestions are non-behavioral (comments, naming, wording).

Overall: the code itself reads well — Allman throughout, `f`-not-`f()` respected, terminology
("route word" = 32-bit fold output vs "slot id" = the `UInt8`) used correctly. The issues are
comment-side: one comment the commit made stale, one fact stated four times (twice verbatim),
one paste of `JoinSlotRouting.h`'s rationale, and a parenthetical that narrates the diff.

## Findings

### 1. Comment made stale by this commit (accuracy)
- **Location:** `src/Interpreters/ConcurrentHashJoin.cpp:385` (`RoutedJoinResult` class doc,
  untouched by the commit)
- **What:** "keeping `joinBlock` as cheap as before (it only derives the route words)". After
  this commit `joinBlock` also builds the `JoinOnKeyColumns` (key materialization, null map,
  ON-section mask), so "only derives" no longer describes it; and the commit renames the
  probe-side "route words" to "slot ids" everywhere else, leaving this sentence (and
  "re-derives its routes" at line 388) on the old vocabulary.
- **Suggested rewording:** "... keeping `joinBlock` cheap (it only prepares the keys and
  derives the slot ids); ..." and at 388: "... which re-prepares its keys and slot ids."

### 2. Same fact stated four times: "keys prepared once and shared"
- **Locations:**
  - `src/Interpreters/ConcurrentHashJoin.cpp:397-398` (`RoutedJoinResult::join_on_keys` member)
  - `src/Interpreters/ConcurrentHashJoin.cpp:452-453` (`joinBlock` body)
  - `src/Interpreters/HashJoin/HashJoin.h:160-161` (`joinRoutedBlock` doc)
  - `src/Interpreters/HashJoin/HashJoinRoutedMethods.h:29-30` (`joinBlockImpl` doc)
- **What:** The last two carry the *identical* sentence: "`join_on_keys` is the block's key
  preparation, built once by the caller and shared with its route derivation." Verbatim
  repetition across files is a generated-text tell; the earlier hygiene pass on this branch
  ("single statement of the build/probe contract") set the one-statement precedent. The coined
  phrase "route derivation" also recurs in all four spots.
- **Suggested rewording:** State it once at the public API (`HashJoin.h`, reworded per finding
  3). In `HashJoinRoutedMethods.h` reduce to "`join_on_keys` is the block's prepared key
  columns (see `HashJoin::joinRoutedBlock`)". The member comment and the `joinBlock` body
  comment can each keep their local half (what the member owns / why it is built here), without
  re-explaining the sharing contract in full.

### 3. "built once by the caller and shared with its route derivation" — dangling "its"
- **Location:** `src/Interpreters/HashJoin/HashJoin.h:161`,
  `src/Interpreters/HashJoin/HashJoinRoutedMethods.h:30`
- **What:** "its" has no clear antecedent (the block's? the caller's?), and "the block's key
  preparation" is an awkward nominalization.
- **Suggested rewording:** "`join_on_keys` holds the block's prepared key columns; the caller
  builds them once and derives `slot_ids` from the same columns."

### 4. Near-verbatim duplication of the `JoinSlotRouting.h` rationale
- **Location:** `src/Interpreters/ConcurrentHashJoin.cpp:590-593` (`computeDispatchSlotIds` doc)
- **What:** "a route word deliberately independent of the CRC32C-family hashes the maps bucket
  by, so slot selection stays decorrelated from `grower.place`" restates, almost word for word,
  the header doc of `src/Interpreters/HashJoin/JoinSlotRouting.h` ("deliberately independent of

- **Suggested rewording:** "The open-addressing types route through the `JoinSlotRouting` fold
  (see there for why the route must stay decorrelated from the maps' own hashes)."
