# Reduce-complexity review — 96136264c16 ("Pool the routed probe's scratch per pipeline lane")

Lens: structural complexity only; all findings are non-behavioral (identical observable
semantics, same documented guarantees). `tmp/` evidence excluded; `src/` only.

Verdict: one real simplification (F1, the redundant `slot_ids` parameter), one dead line
(F2), and a handful of trivia. The pool itself is near-minimal for its documented contract
(F4) — the mutexed fallback pool is load-bearing and should stay.

---

## F1 — `slot_ids` is a redundant parameter now that it lives inside `scratch` (main finding)

**Location:**
- `/mnt/ch/ClickHouse/src/Interpreters/ConcurrentHashJoin.cpp:483-489` (call site: passes
  `scratch->slot_ids.empty() ? nullptr : scratch->slot_ids.data()` AND `scratch.get()`)
- `/mnt/ch/ClickHouse/src/Interpreters/HashJoin/HashJoin.h:166-171` and
  `/mnt/ch/ClickHouse/src/Interpreters/HashJoin/HashJoin.cpp:1047-1105` (`joinRoutedBlock`)
- `/mnt/ch/ClickHouse/src/Interpreters/HashJoin/HashJoinRoutedMethods.h:31-71` (4 declarations)
- `/mnt/ch/ClickHouse/src/Interpreters/HashJoin/HashJoinRoutedMethodsImpl.h:17-18, 51,
  106-107, 138-139, 155-156, 172, 196-199, 211-212, 302, 350, 362, 514, 536` (definitions,
  forwarding sites, and the two real consumers)

**What:** The whole chain `joinRoutedBlock → joinBlockImpl → switchJoinRightColumns →
joinRightColumnsRouted → joinRightColumns` carries BOTH `const UInt8 * slot_ids` and
`JoinProbeScratch * scratch`, but since this commit the slot ids ARE `scratch->slot_ids`:
the single caller (`RoutedJoinResult::next`) derives the pointer from the very scratch it
passes one argument later. `joinBlockImpl` and `switchJoinRightColumns` never read
`slot_ids` — they only forward it. The only consumers are `joinRightColumnsRouted` (the
`routed_ctx{.slot_ids = ...}` at Impl:172) and `joinRightColumns` (per-row `slot_ids ?
slot_ids[ind] : 0` at Impl:302/350/362 and the `amacFindPass` argument at Impl:536).

**Why non-behavioral:** `joinRoutedBlock` has exactly one caller in the tree
(`ConcurrentHashJoin.cpp:483`; verified — no gtest or other caller). That caller always
passes a non-null scratch (`acquireProbeScratch` never returns null), and the
`empty() ⇔ nullptr` mapping is exactly what the caller computes today, so deriving the
pointer inside the chain produces bit-identical control flow, including the rows==0 and
single-slot cases.

**Suggested change (exact):**
1. Delete the `const UInt8 * slot_ids` parameter from all five signatures
   (`HashJoin::joinRoutedBlock`, `RoutedHashJoinMethods::{joinBlockImpl,
   switchJoinRightColumns, joinRightColumnsRouted, joinRightColumns}`) and from the ~8
   forwarding sites (including the three `joinDispatch` lambda branches in `HashJoin.cpp`
   and the `M` macro expansion at Impl:138).
2. In the two consumers, derive locally at function entry:
   `const UInt8 * slot_ids = scratch->slot_ids.empty() ? nullptr : scratch->slot_ids.data();`
3. While at it, take `JoinProbeScratch &` instead of `JoinProbeScratch *` through the chain
   (the producer guarantees non-null): this deletes the `chassert(scratch)` at Impl:514 and
   the `[[maybe_unused]]` on the parameter at Impl:212 (scratch becomes unconditionally used
   once it also supplies `slot_ids`).
4. The call site in `RoutedJoinResult::next` collapses to
   `joinRoutedBlock(slot_joins, std::move(block), *scratch, std::move(join_on_keys))`,
   removing the awkward ternary.
5. Update the two doc comments that describe the `slot_ids` argument
   (`HashJoin.h:160-162`, `HashJoinRoutedMethods.h:28-30`) to say the slot ids ride in the
   scratch (`slot_ids` empty ⇔ single slot).

Net: ~15 lines removed and one fewer parameter to keep coherent across five functions.
A minimal variant, if the internal chain is meant to stay generic: drop `slot_ids` only from
`joinRoutedBlock` and derive it there — that alone fixes the caller-side redundancy.

## F2 — dead `using IJoin::joinBlock;` in ConcurrentHashJoin.h

**Location:** `/mnt/ch/ClickHouse/src/Interpreters/ConcurrentHashJoin.h:57`

**What:** `ConcurrentHashJoin` overrides BOTH overloads (`joinBlock(Block)` at :58 and
`joinBlock(Block, size_t)` at :59), so nothing from the base is hidden and the
using-declaration is inert — the derived declarations shadow the members it brings in.

**Why non-behavioral:** a using-declaration whose members are all re-declared in the same
class affects neither overload resolution nor the vtable. `-Woverloaded-virtual` cannot fire
when every base overload is overridden (verified with a minimal repro under
`-Woverloaded-virtual -Werror`: the both-overridden class is clean, the one-overridden class
warns).

**Suggested change:** delete line 57. (Keeping it "for symmetry" with the other 8 files is
defensible; under this lens it's a dead line.)

## F3 — the 8 wrapper/`IJoin`-subclass `using` insertions: correct, necessary, consistent

**Location:** `ConstantJoin.h:51`, `DirectJoin.h:41`, `FullSortingMergeJoin.h:124`,
`GraceHashJoin.h:80`, `JoinSwitcher.h:39`, `MergeJoin.h:45`, `PasteJoin.h:58`,
`SpillingHashJoin.h:80`.

**What/verdict:** each is placed immediately before the class's `joinBlock` override —
consistent across all 8 — and each is required: these classes override only the 1-arg
overload, which would hide the new 2-arg virtual and trip `-Woverloaded-virtual` (in
clang's `-Wall` via `-Wmost`; builds are `-Werror`). Coverage is complete: all 10 `IJoin`
subclasses in the tree now have the using (`HashJoin.h:152` already had one since
16ddf20c73a), so no subclass was missed. No defect.

**Optional structural alternative (judgment call, not a request):** giving the lane-carrying
entry point a distinct name in `IJoin` (e.g. `joinBlockForLane`) would remove the overload
set entirely — all 9 `using` lines go away, and future `IJoin` implementors stop paying the
recurring "add the using or fail the build" tax. Cost: two names for one concept. The
current overload+using shape is idiomatic for this codebase; flagged only because the 9
sprinkled `using` lines are exactly the kind of accretion this lens looks for.

## F4 — the parking table + mutexed pool: near-minimal; do NOT fold them together

**Location:** `/mnt/ch/ClickHouse/src/Interpreters/ConcurrentHashJoin.cpp:272-307`,
`ConcurrentHashJoin.h:140-146`.

**What was checked:** whether the two-tier structure (lock-free per-lane slots + mutexed
overflow pool) could be collapsed without losing the documented guarantees ("never lost,
never double-owned", no per-block allocation in steady state).

**Verdict:** no. The obvious collapse — drop the pool and delete a scratch on
release-collision / allocate on miss — keeps the ownership guarantees but silently turns the
lane-less path into allocate-per-probe-block: `SpillingHashJoin::joinBlock`
(`SpillingHashJoin.cpp:307`) forwards lane-less into `ConcurrentHashJoin::joinBlock(Block)`
→ `invalid_lane` → pool path on EVERY probe block, so the pool is load-bearing there, not
just a collision escape hatch. Collapsing the other way (mutexed pool only) forfeits the
lock-free fast path the commit exists to provide. The current ~40 lines are about the
minimum for the stated contract.

**Micro-alternative (optional, ~3 lines, same guarantees):** `releaseProbeScratch` could use
an unconditional `exchange` instead of the CAS — park the incoming scratch, pool the
previous occupant if any:
```cpp
if (lane < probe_scratch_slots.size())
{
    scratch.reset(probe_scratch_slots[lane].exchange(scratch.release(), std::memory_order_acq_rel));
    if (!scratch)
        return;
}
```
This removes the `expected` variable and the NOLINT'd `scratch.release()`-inside-`if` dance.
Equivalent ownership outcome (on collision, one of the two ends up parked and one pooled —
just the other one). Slightly more clever, slightly fewer moving parts; take it or leave it.

Also verified as fine: `probe_scratch_slots(2 * slots)` sizing is documented and the member
init order is safe (`slots` is declared before `probe_scratch_slots`); the destructor's raw
`delete slot.load(...)` is the only way to drain `vector<atomic<T*>>` and is commented.

## F5 — trivia

1. **`JoiningTransform.h:91`** — `size_t stream_index = 0;`: the in-class initializer is
   dead; the constructor unconditionally assigns it from `stream_index_` (which itself
   defaults to 0). Neighboring `max_block_size` carries no initializer. Drop the `= 0` for
   consistency. Non-behavioral: the member is always constructor-initialized.
2. **`ConcurrentHashJoin.h:10`** — new `#include <limits>` lands mid-block between
   `base/types.h` and `Common/ThreadPool_fwd.h`; per `.clang-format` (`SortIncludes: true`,
   std headers priority 1) std headers group first, next to the existing `<memory>`.
   Cosmetic; the block was already unsorted before this commit.
3. **`HashJoinRoutedMethods.h`** — uses `JoinProbeScratch *` in four declarations while
   relying on the forward declaration in directly-included `HashJoin.h:30`. Acceptable;
   a local `struct JoinProbeScratch;` would make the header self-describing. (Moot if F1's
   reference-passing lands — the fwd decl is still all that's needed.)
   Other include hygiene is clean: `JoinProbeScratch.h` is a minimal leaf header (both of
   its includes are used); `HashJoinRoutedMethodsImpl.h`'s new include is used; the full
   include in `ConcurrentHashJoin.h` is justified (gtests dereference the pooled scratch
   through this header).
4. **`ConcurrentHashJoin.cpp:533`** — `scratch->slot_ids.clear()` in the `slots == 1` branch
   is a no-op in practice (the pool is per-join and a single-slot join never fills
   `slot_ids`), but it is the one-line guard the `empty() ⇔ single-slot` contract rests on
   and becomes the single source of truth under F1. Keep.
5. **Vocabulary** — `IJoin` says "lane", `JoiningTransform` says "stream_index". The
   transform-side name matches its pre-existing sibling (`NonJoinedBlocksTransform`'s
   `stream_index`), and the `IJoin.h` comment ties the two together, so no change needed;
   noted only so a future rename doesn't pick a third word.
